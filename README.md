# Лабораторная работа: Информационная система для управления объектами класса `Ticket`
 
## Постановка задачи
 
Реализовать информационную систему, которая позволяет взаимодействовать с объектами класса `Ticket`, описание которого приведено ниже.

## Требования к системе
 
### Основное назначение
 
Управление объектами, созданными на основе заданного в варианте класса.
 
### Операции с объектами
 
Система должна поддерживать выполнение следующих операций, каждая в отдельном окне (интерфейсе) приложения:
 
1. **Создание** нового объекта
2. **Получение** информации об объекте по ID (с выводом информации о связанных объектах)
3. **Обновление** объекта (модификация атрибутов)
4. **Удаление** объекта
При создании объекта пользователь должен иметь возможность связать его с уже существующими в системе объектами вспомогательных классов.
 
> Все операции по управлению объектами должны выполняться на серверной части (не на клиенте), с синхронизацией изменений с базой данных.
 
### Главный экран
 
- Список текущих объектов выводится в виде **таблицы** (каждый атрибут — отдельная колонка).
- При большом количестве объектов используется **пагинация**.
- Поддерживаются **фильтрация** (по неполному совпадению) и **сортировка** строк по значениям любой строковой колонки.
- Переход к обновлению объекта возможен как из таблицы, так и из области визуализации объекта (при её наличии).
### Синхронизация и целостность данных
 
- При добавлении/удалении/изменении объекта изменения должны **автоматически отражаться** в интерфейсах у всех других авторизованных пользователей.
- При удалении объекта, с которым связаны другие объекты, связанные объекты должны быть **переприкреплены к другому объекту по выбору пользователя**, после чего исходный объект удаляется.
### Пользовательский интерфейс
 
- Просмотр всех объектов доступен всем пользователям.
- Модификация объекта выполняется в отдельном диалоговом окне.
- При некорректном вводе должны выводиться **информативные сообщения об ошибках**.
### Специальные операции
 
Отдельный пользовательский интерфейс должен реализовывать следующие операции бизнес-логики (без прямого использования функций/процедур БД):
 
1. Вернуть количество объектов, значение поля `number` которых меньше заданного.
2. Вернуть массив объектов, значение поля `name` которых начинается с заданной подстроки.
3. Вернуть массив уникальных значений поля `number` по всем объектам.
4. Продать билет за указанную сумму указанному человеку.
5. Скопировать указанный билет, создав такой же, но с категорией `VIP` и удвоенной ценой.

## Особенности хранения данных
 
- Данные хранятся в реляционной СУБД **PostgreSQL**.
- Все требования к полям класса (см. таблицы выше) реализуются на уровне **ORM и БД**.
- Поле `id` генерируется средствами базы данных.
- Подключение к БД на кафедральном сервере:
  - хост: `pg`
  - имя базы данных: `studs`
  - имя пользователя/пароль — совпадают с учётными данными для подключения к серверу.
## Особенности взаимодействия с пользователем
 
- Система должна реагировать на некорректный пользовательский ввод, ограничивая ввод недопустимых значений и информируя о причине ошибки.
- Переходы между логически обособленными частями системы осуществляются через **меню**.
- Изменения объектов автоматически отражаются в интерфейсах всех клиентов.
## Технологические требования
 
- Основа реализации — **Jakarta EE**, **CDI beans**.
- Уровень хранения данных — **Hibernate**.
- Разные уровни приложения должны быть разделены; логические части системы — в отдельных компонентах.
